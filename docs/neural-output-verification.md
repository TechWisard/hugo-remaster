# DLSS-NR: от сообщений backend к проверке экранного кадра

## Что установлено

В предоставленном пользователем отчёте `Verify-Hugo-DLSS5.cmd` все четыре
маркера GITC 1.8 были истинными: OpenGL-мост, созданная NR-feature, включённый
evaluate и возврат кадра. Проверка файлов была успешной; ошибок backend в
JSON не перечислено. Сам отчёт явно оставлял качество и производительность
непроверенными. Из этого нельзя делать вывод, что в Hugo отсутствовала DLL
или вообще не вызывался нейросетевой проход.

Проверен исходный код GITC-Uplift версии 1.8.0, commit
`0d73f2102032dcf8df24c7ff0f18315911f4af59`. Используются
[релиз 1.8.0](https://github.com/ghostinthecamera/GITC-Uplift/releases/tag/v1.8.0)
и соответствующие исходники, без исполнения библиотеки Windows в среде Linux.

| Участок | Проверенное поведение | Предел доказательства |
| --- | --- | --- |
| [src/nr/feature.cpp](https://github.com/ghostinthecamera/GITC-Uplift/blob/0d73f2102032dcf8df24c7ff0f18315911f4af59/src/nr/feature.cpp) | Сообщение включённого evaluate появляется после успешного NGX-вызова при ненулевой интенсивности и выключенном bypass | Не является чтением итоговых пикселей с GPU |
| [src/bridge/gl_bridge.cpp](https://github.com/ghostinthecamera/GITC-Uplift/blob/0d73f2102032dcf8df24c7ff0f18315911f4af59/src/bridge/gl_bridge.cpp) | CopyIn, синхронизация GL↔D3D12, evaluate, синхронизация назад, CopyOut в кадр игры; маркер возврата выдаётся один раз за включение | Маркер сообщает о пройденном программном пути; не даёт счётчик всех реально показанных кадров или readback |

В preset ремастера `Lumenite_Kernel` стоит перед `Uplift`, после Uplift
других эффектов нет. В рассмотренном коде не найдено доказанного места,
которое неизбежно затирает NR-выход исходным кадром. Поэтому исправление
не называется «найденным composition bug». Параметры силы и смеси теперь
явно записаны в новом шаблоне и показаны в Verify.

Проверено и сопоставление адаптера: OpenGL LUID используется, когда драйвер
его предоставляет; в fallback исходник выбирает первый NVIDIA-адаптер DXGI.
Это ограничение пути с несколькими адаптерами, а не установленная причина
на машине пользователя. Две строки выбора GPU сами по себе не доказывают
два физических устройства.

## Живой статус игровой сессии

Параметры движка передаются после Godot-разделителя `--`:

```text
--nr-status-file=<absolute JSON path>
--nr-session=<32-character launch nonce>
```

Пример структуры без выдуманного счётчика:

```json
{
  "schema": 1,
  "session": "0123456789abcdef0123456789abcdef",
  "provider": "gitc_uplift_opengl",
  "state": "backend_reported",
  "reason_code": "backend_frame_reported_display_unverified",
  "frames_processed": null,
  "updated_utc": "2026-11-09T20:00:00.0000000Z",
  "process_id": 1234,
  "display_output_verified": false
}
```

Значения PID и времени выше служат примером формата. Рабочий файл создаётся
запускателем в каталоге отдельной сессии, атомарно заменяется и получает
heartbeat раз в секунду. Игра проверяет session, собственный PID, schema и
возраст heartbeat. Отсутствующий, чужой или просроченный файл не становится
подтверждением NR. В игре читатель ничего не записывает и не загружает DLL.

`probing` означает ожидание сообщения текущей игры. После 30 секунд без
нужного сообщения появляется `inactive` с причиной; позднее успешное
сообщение может изменить состояние. `backend_reported` означает четыре
свежих маркера текущего запуска, без утверждения об экранном результате.
`inactive` также используется при выключении NR, нулевой интенсивности,
нулевой смеси и чистом рендерере. `failed` отражает наблюдаемую ошибку.
После F8 Off старые маркеры не подтверждают активность; F8 On требует
нового сообщения о возврате кадра.

Чистый fallback получает `provider=none` и конкретную причину, например
`neural_preflight_not_confirmed`, `angle_clean_fallback` или `forced_clean`.
Проверочная сцена и кэш совместимости не пишут положительный живой статус
вместо настоящей игры. Исходный ReShade.log архивируется перед её стартом;
файл, уже существовавший при запуске наблюдателя, не используется как
доказательство даже после изменения его времени.

## Отдельная проверка экранного результата

`Check-Hugo-NR-Image.cmd` запускает только asset-free диагностическую сцену.
`native_graphics_probe.gd` фиксирует геометрию, камеру и освещение, продолжает
показывать одинаковые кадры и принимает команды через JSON с nonce. На каждый
запрос он возвращает SHA-256 полного native framebuffer, позу, размер, PID и
номер запроса. Это вход до внешнего present, поэтому он не выдаётся за
результат NR.

Windows-helper использует `Graphics.CopyFromScreen` для клиентской области
своего окна. Это захват рабочего стола после ReShade, а не `PrintWindow` и
не Godot viewport capture. До и после захвата проверяются PID окна, фокус,
сворачивание, положение, размер, границы рабочего стола и перекрывающие
видимые окна выше него. Неоднозначный захват даёт `inconclusive`.

Последовательность: Off A, Off B, On A, On B, Off Return. F8 привязан к
`EnableKey=119` самого Uplift; общий выключатель ReShade не используется.
Lumenite остаётся включённым, дополнительные post-effects исключены.
При включении helper ждёт свежего подтверждения backend. После каждой
перемены оставляется время для установления temporal-состояния.

Для положительного результата должны одновременно выполниться условия:

1. Все native framebuffer hashes и позы совпадают, session и PID относятся
   к текущей пробе, размеры native и desktop одинаковы.
2. Окно является активным и не перекрывается на проверках захвата.
3. Off A/Off B и Off A/Off Return стабильны: средняя RGB-разность не более
   0,05 из 255; число пикселей с изменением хотя бы одного канала больше 3
   не превышает 0,01% площади, с минимальным допуском 16 пикселей.
4. В центральных 70% ширины и высоты On/Off среднее изменение больше
   0,25 из 255 и в десять раз выше шума Off; изменено больше 0,1% центральной
   области, с минимальным порогом 256 пикселей.
5. On A/On B достаточно устойчивы: среднее центральное изменение не больше
   максимума из 0,1 и половины On/Off-разницы. Однотонные/пустые захваты
   не принимаются.

Пороги — правила этой диагностической проверки, не измерение качества
нейронной модели. `display_change_verified` подтверждает воспроизводимую
экранную разницу именно на пробе. `no_visible_change` сообщает отсутствие
заметной разницы при соблюдённых контролях. Нарушенный контроль означает
`inconclusive`, даже если backend ранее сообщал об evaluate.

Шаблон сохраняет PNG, diff с увеличением яркости 4×, численные метрики,
журнал backend и ответы движка. `visual_quality_validated` и
`benchmark_validated` остаются false. Результат отдельной пробы не
подменяет live-status другого игрового процесса.

## Проверено локально и что остаётся проверять на Windows

Проверены атомарная публикация, session/PID аргументы, различение старого
журнала и текущего процесса, disable/re-enable, нулевая смесь и логика
классификации. Наблюдатель прошёл тест с имитированным процессом, без
исполнения EXE игры или сторонней Windows-библиотеки. Код C# скомпилирован;
сравнение одинаковых RGB-буферов, известного изменения каждого канала на 10
и однотонного буфера проверено отдельно.

Реальный OpenGL-прогон frozen handshake дал три одинаковых полных кадра
1280×720. Рендерер этой среды — Mesa llvmpipe, поэтому отчёт оставил
`hardware_verified=false`. Утверждений об NR на RTX из этого не следует.
Win32-захват, F8-протокол именно с установленным ReShade и вывод на RTX 4090
здесь не выполнялись. Они требуют запуска готового helper на Windows.
